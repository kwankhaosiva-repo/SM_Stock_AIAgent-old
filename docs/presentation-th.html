บทที่ 01

จุดเริ่มต้น — ทำไมถึงเริ่มทำ

จุดเริ่มต้นคือคำถามสั้น ๆ ว่า: "มีผู้ช่วยดูหุ้นที่เชื่อถือได้ คุยกันบน LINE ได้ แล้วบอกได้เสมอว่าแต่ละข้อความอ้างอิงอะไรมา?"

เริ่มจากบอทง่าย ๆ ที่ต่อ LLM ตัวเดียวแล้วถามตอบเรื่องหุ้น แต่การใช้งานจริงเผยปัญหาสามชั้นทันที:

  • LLM ที่ใช้อยู่วันดีคืนดีใช้ไม่ได้ — quota หมด, ค่าบริการตัด (เคส Gemini credits หมดจน API ตอบ 402), model ที่ตั้งไว้โดนถอด (404)
  • คำตอบที่ได้ “ดูดีแต่ตรวจสอบไม่ได้” — AI มักเดาตัวเลขราคา P/E หรือแต่งเหตุผลลอย ๆ ให้ฟังดูน่าเชื่อ
  • ข้อมูลตลาดจริงดึงยาก — หลาย API บล็อก IP คลาวด์, ข้อมูลหุ้นไทยมี official feed แต่เข้าถึงจำกัด

ปัญหาเหล่านี้กลายเป็น หลักการออกแบบสามข้อ ของโปรเจกต์ ที่ทุกส่วนในระบบต้องยึดตาม:

  • 1. ห้ามให้ AI คิดเลข — ตัวเลขทุกตัวต้องมาจาก Python/pandas ที่ตรวจสอบได้ LLM มีหน้าที่ “ตีความ” เท่านั้น
  • 2. ทุกเหตุผลต้องบอกที่มา — แยกเป็น [จากข่าว] / [จากงบ] / [จากสถิติ] เสมอ พร้อมเลขอ้างอิงข่าวต้นฉบับ
  • 3. ระบบต้องไม่ล่มเมื่อ provider เดียวมีปัญหา — สาย failover อัตโนมัติทั้ง LLM, ข้อมูลตลาด และการส่งข้อความ
บทที่ 02

ปัญหาที่เจอระหว่างทาง และคำตอบของเรา

pain point ที่เจอจริงคำตอบที่ลงมือทำ
พึ่ง LLM เจ้าเดียว = จุดเสี่ยงเดียว
quota หมด / ค่าบริการตัด / model ถูกถอด = ระบบหยุดทั้งระบบ		 Provider chain 8 เจ้า พร้อม context-forwarding failover — ล้ม (429/404/timeout/no key) แล้วส่ง prompt + context ชุดเดิมไปเจ้าถัดไปอัตโนมัติ พร้อม 404 self-heal ดึงรายการ /models จริงมาเลือก model ใหม่

การ์ด LINE ยาว อ่านยาก เยอะไปหมด Progressive disclosure + scanable tags — สรุปสั้น 2 บรรทัดก่อน, กด News คดูเต็ม, ทุกเหตุผลมี tag แหล่งที่มา + ป้ายไฟจราจร 🟢🔴🟡 ให้สแกนก่อนอ่าน
บทที่ 03

ทำไมถึงเลือกวิธีนี้ — เหตุผลเชิงออกแบบ

ทุกทางเลือกเชิงเทคนิคมาจากปัญหาในบทที่ 02 ไม่ใช่เลือกเพราะ "ฮิต"

ทำไมต้องเป็นสาย failover หลายเจ้า ไม่ใช่ API เดียวที่เสถียร?

เพราะฟรี Tier ของแต่ละค่าย ไม่มีอันไหนรับประกันได้ — โควตารายวันหมดเร็ว, เปลี่ยน model บ่อย, บางค่ายปิดตัวลง การผูกกับเจ้าเดียวเท่ากับยอมรับจุดเสี่ยงเดียว
ทางออกแบบ: ลำดับเรียก configurable (LLM_PROVIDER_ORDER) — ตอนนี้ groq → cerebras → mistral → cloudflare → openrouter → unorouter → router9 → ollama ล้มเหลวแล้วส่ง prompt + context ชุดเดิมต่อไปให้เจ้าถัดไป (ไม่ใช่เริ่มใหม่) และถ้า model โดนถอด (404) จะดึง /models จริงมาเลือกตัวที่ใกล้ที่สุดแล้ว cache ไว้ — env ที่ตั้ง model ชื่อเก่าไว้จึงไม่ทำให้ระบบพัง

ทำไมคิดเลขด้วย Python ไม่ใช่ให้ LLM คำนวณ?

เพราะโมเดลภาษาไม่เหมาะกับตัวเลข — ราคา RSI หรือ P/E ที่ AI "จำ" ได้คือตัวเลขที่แต่งขึ้นมา ทำให้คำแนะนำดูน่าเชื่อแต่ใช้ไม่ได้จริง
ทางออกแบบ: indicators.py (RSI-14, SMA-20/50, ความผันผวน, แนวรับ-ต้านจาก 30 วัน, 52 สัปดาห์) และ financial_ratios.py (D/E, ROE, P/B, net margin) คำนวณจาก pandas/ตัวเลขงบจริง — LLM ได้รับตัวเลขเหล่านี้เป็น บริบท แล้วแค่ตีความและเรียบเรียง

ทำไมต้องมี chain สำหรับข้อมูลตลาดด้วย?

เพราะข้อมูลการเงินก็มีจุดเสี่ยงคล้าย LLM: Settrade sandbox จำกัด IP ไทย, finnhub บน GCP โดนบล็อก, Yahoo บางครั้ง rate-limit
ทางออกแบบ: สาย provider ที่ ข้ามไปตัวถัดไปเมื่อเจอ skip — หุ้นไทย: Settrade → home relay (IP บ้านผ่าน Cloudflare Tunnel) → helper → yfinance; หุ้นทั่วโลก: relay → yfinance และข่าว: Finnhub (US, ทางการ) → Google News RSS (ไทย + มาโคร)

ทำไมย้ายจาก PostgreSQL/SQLAlchemy มาเป็น Firestore?

เพราะระบบนี้เป็น webhook + cache + audit log ไม่ใช่ relational workflow ที่ซับซ้อน — การใช้ ORM เต็มรูปแบบทำให้มี migration, connection pool, cold start ที่ไม่จำเป็น
ทางออกแบบ: store.py ชั้นเดียวสอง backend — Firestore (prod, ADC บน Cloud Run ไม่ต้องตั้ง secret เพิ่ม, lazy init) / in-memory (dev & test, DATA_BACKEND=memory) ย้ายออกจาก Supabase เมื่อ ก.ย. 2026 ลบ ORM กับ migration ทิ้งหมด

ทำไมใช้ LangGraph?

เพราะงานวิเคราะห์ 1 ครั้ง = 4 หน้าที่ที่รันขนานกันได้ (ข่าว / พื้นฐาน+เทคนิค / คำแนะนำ / ตรวจสอบ) และต้องการจุดตรวจสอบกลาง บันทึกผลแต่ละขั้นลง audit trail
ทางออกแบบ: report_workflow.py — StateGraph แบบ fan-out ขนาน + reflection loop ให้ RiskReviewer ส่งกลับมาแก้ และ log ทุก stage ลง Firestore (analysis_runs / agent_outputs)

ทำไมเป็น Flask เล็ก ๆ ไม่ใช่ framework ใหญ่?

งานหลักคือรับ webhook, โยนงานเข้าคิว, คืนคำตอบ — ไม่ต้องการ ORM, DI container หรือ overhead
ทางออกแบบ: Flask 3 + gunicorn (timeout 240 วิ รองรับการรอ AI), คิวเป็น RQ/Redis ตอน prod และ fallback เป็น thread-pool บนเครื่อง dev — โค้ดเดียวกันรันได้ทั้งสองแบบ

บทที่ 05

สายคิดของ AI — 4 เอเจนต์ กฎอย่างหนึ่ง

ระบบไม่ได้ “คุยกับ chatbot หนึ่งตัว” แต่แบ่งงานเป็น 4 เอเจนต์ แต่ละตัวมี soul (ไฟล์ Markdown ของ system prompt) เก็บใน git แก้ไข ตรวจสอบเวอร์ชันได้

เอเจนต์หน้าที่
NewsContextAgentกรอง-จัดอันดับข่าวบริษัท + ข่าวมหภาค เก็บ provenance ครบ (หัวข้อ, สำนัก, URL, เวลา)
FundamentalTechnicalAgentตีความราคา, P/E, ปันผล, ตัวชี้วัดเทคนิคที่คำนวณไว้แล้ว — ห้ามเดาราคา ห้ามคำนวณ indicator เอง
PersonalizedAdviceAgentสังเคราะห์เข้ากับสไตล์การลงทุน เป้าหมาย ความเสี่ยงที่รับได้ ของผู้ใช้ → เหตุผล 3 หมวด + ความเสี่ยง + สิ่งต้องติดตาม
RiskEvidenceReviewerผู้ตรวจสอบอิสระ — ปฏิเสธข้อความที่ไม่มีหลักฐาน, ข้อมูลเก่า >15 นาที, คำต้องห้าม (“การันตี”, “กำไรแน่นอน”) คืน approve / revise / reject
สัญญาอ้างอิงหลักฐาน (evidence contract) ทำงานอย่างไร?

ข่าวทุกชิ้นถูกทำความสะอาดและจัดอันดับก่อน (ตัด URL ขยะ, ตัดหัวข้อซ้ำข้ามสำนัก, ให้ impact score) แล้วใส่เลขลำดับ [1] [2] … เข้า prompt — LLM ต้องอ้างเลขเหล่านี้เท่านั้น ตัวเลข citation ที่โชว์บนการ์ด detail จึงมาจาก digest จริง ส่วนบนการ์ดสรุปจะถูกตัดออกเพื่อความอ่านง่าย และข้อความทุกบรรทัดถูก clean: ตัด URL, ตัด citation, ตัด placeholder “ไม่มีข้อมูล…”

บทที่ 06

UX Engineering — ออกแบบให้อ่านจบใน 5 วินาที

⏳ Instant ack + กันกดซ้ำ

ทุกปุ่มตอบ “กำลังประมวลผล…” ทันที ไม่มี dead air และล็อก 30 วินาทีต่อ user+action+symbol — กดซ้ำได้คำตอบว่า “กำลังทำอยู่” แทนที่จะยิง AI ซ้ำ

📚 Progressive disclosure

การ์ดสรุปโชว์หัวข้อข่าวแบบเทเลกราฟ 2 บรรทัด — กดปุ่ม News คดูการ์ดเต็ม เรียงตามผลกระทบ พร้อมปุ่มเปิดต้นฉบับ (URL มาจาก digest เท่านั้น ไม่ใช่ที่ AI แต่ง)

🏷 เหตุผลแยก 3 หมวด — พร้อม tag หน้าทุกบรรทัด

ทุกเหตุผลขึ้นต้นด้วย tag แหล่งที่มาเสมอ ให้ผู้อ่านรู้ทันทีว่าข้อไหนอ้างอิงอะไร:

📰 [จากข่าว] 🏦 [จากงบ] 📊 [จากสถิติ]

ใช้กับทุกการ์ด: stock card, market brief และ daily digest (ทั้งแบบ flex และ plain-text fallback)

🚦 ป้ายไฟจราจรทุกบรรทัด

ทุกบรรทัดคำแนะนำและเหตุผลมีป้ายกำกับให้สแกนก่อนอ่าน — ไม่เดาเองว่าดีร้าย:

🟢 Positive 🔴 Negative 🟡 Watch

จำแนกด้วย keyword classifier (ไทย+อังกฤษ) กรณีไม่แน่ใจจะ fallback เป็น 🟡 Watch เสมอ — ไม่มีบรรทัดไหนไร้ป้าย

🗞 ข่าว: ดึงกว้างก่อน คัดทีหลัง — บอกตัวเลขให้เห็น

pipeline ข่าวไม่ได้ดึงมา 8 ข่าวแล้วใช้เลย แต่ ดึงกว้างก่อนแล้วคัด:

  • ดึง (raw): Finnhub company news สูงสุด 20 ชิ้น (7 วันล่าสุด, US) หรือ Google News RSS 10 ข่าวบริษัท + 10 ข่าวมหภาค
  • คัด (clean + dedupe + rank): ตัดขยะ/หัวข้อซ้ำ ให้ impact score แล้วเลือก Top 8
  • รายงาน: log [NewsPipeline] raw=M -> kept=N และการ์ดโชว์ “คัด 8 จากที่ดึงมา 23 ข่าว” ให้รู้ว่ามีการคัดจริง

บทที่ 09

ทดสอบ & ส่งขึ้น Production

การทดสอบ

  • 40 unit tests รันแบบ offline ได้ (DATA_BACKEND=memory python -m unittest discover -s tests) — ไม่ต้องมี network ไม่ต้องมี key
  • ครอบคลุม: การ render การ์ดทุกประเภท, หมวดเหตุผล, tone classifier, idempotency, cache, workflow

การ deploy

  • Git push → Cloud Run auto-deploy (asia-southeast1, service: agent-stocks-service)
  • Secret: อัปโหลดไฟล์ .env ทั้งหมดเป็น secret ชื่อ env_stocks mount เป็น ENV_STOCKS — ค่าใน secret override default ใน config.py
  • gunicorn: --timeout 240 --max-requests 200 กัน worker ค้าง/หนักเกินไป
  • debug ผ่าน /health และ /debug/config (โชว์ว่า env ตัวไหนถึง container โดยไม่โชว์ค่า)
