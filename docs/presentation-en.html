CHAPTER 01

Origin — why this project started

It began with a short question: "Why isn't there a stock assistant I can trust — one I can talk to on LINE, and that can always show me what each claim is based on?"

The first version was a simple bot wired to a single LLM. Real usage immediately exposed three layers of problems:

  • The LLM provider would randomly stop working — daily quota exhausted, billing cut off (the Gemini credits-depleted 402 case), configured models deprecated (404)
  • Answers looked good but couldn't be verified — the model would invent prices, P/E ratios, or plausible-sounding reasons
  • Real market data was hard to fetch — many APIs block cloud IPs; official Thai-market feeds are access-restricted

These became the project's three design laws, obeyed by every component:

  • 1. The AI never does the math — every number comes from auditable Python/pandas; the LLM only interprets
  • 2. Every reason must declare its source — tagged [news]/[from financials]/[from stats] (shown in Thai as [จากข่าว]/[จากงบ]/[จากสถิติ]), with real numbered news citations
  • 3. One provider failing must not take the system down — automatic failover across LLM, market data, and delivery

CHAPTER 03

Why we chose this way — the design reasoning

Every technical choice traces back to a problem from Chapter 02 — not to what's trendy.

Why a multi-provider failover chain instead of one reliable API?

Because no free tier is guaranteed — daily quotas burn out fast, models change frequently, some providers shut down. Locking into one vendor means accepting one point of failure.
Design: a configurable call order (LLM_PROVIDER_ORDER) — currently groq → cerebras → mistral → cloudflare → openrouter → unorouter → router9 → ollama. On failure the same prompt + context is forwarded (never restarted), and on 404 the provider fetches the real /models list, picks the closest model, and caches it — stale model names in env vars can no longer break the chain.

Why compute with Python instead of letting the LLM calculate?

Because language models are bad at numbers — an RSI or P/E the model "remembers" is an invented number that makes advice look credible while being wrong.
Design: indicators.py (RSI-14, SMA-20/50, volatility, 30-day support/resistance, 52-week range) and financial_ratios.py (D/E, ROE, P/B, net margin) computed from pandas and raw balance-sheet values — the LLM receives these as context and only interprets and phrases them.

Why does market data need a chain too?

Because market data has failure modes like LLMs: Settrade's sandbox is Thai-IP-only, Finnhub is blocked from GCP IPs, Yahoo rate-limits occasionally.
Design: a provider chain that skips to the next on rejection — Thai stocks: Settrade → home relay (your residential IP via Cloudflare Tunnel) → helper → yfinance; global: relay → yfinance. News: Finnhub (official, US) → Google News RSS (Thai + macro).

Why migrate from PostgreSQL/SQLAlchemy to Firestore?

Because this system is webhooks + cache + audit logs, not a complex relational workflow — a full ORM brought migrations, connection pools, and cold-start overhead for nothing.
Design: one store.py with two backends — Firestore (prod; Application Default Credentials on Cloud Run mean zero extra secrets; lazy init) / in-memory (dev & tests via DATA_BACKEND=memory). Migrated from Supabase in Sep 2026; ORM and migrations removed.

Why LangGraph?

Because one analysis run = four duties that fan out in parallel (news / fundamentals+technicals / advice / review) and needs a central checkpoint logging every stage.
Design: report_workflow.py — a StateGraph with parallel fan-out + a reflection loop where the RiskReviewer can send work back, every stage audited to Firestore (analysis_runs / agent_outputs).

Why a small Flask app instead of a big framework?

The core job is receiving webhooks, enqueueing work, and replying — no ORM, DI container, or heavy machinery needed.
Design: Flask 3 + gunicorn (240-s timeout to survive AI calls), RQ/Redis queue in production with an automatic local thread-pool fallback in dev — the same code runs both ways.

Three resilience layers

1 · LLM chain

8 providers in configured order; failures forward context automatically; 404 self-heal from the live /models list

2 · Data chain

Prices/fundamentals/news skip to the next provider on blocks, including a home relay via Cloudflare Tunnel

3 · Delivery

UUID retry key + Firestore idempotency = zero duplicate pushes; rejected Flex payloads still get a plain-text fallback

CHAPTER 05

The AI pipeline — four agents, one hard rule

This isn't "one chatbot" — work is split across four agents, each with a version-controlled soul (a Markdown system-prompt file kept in git).

AgentResponsibility
NewsContextAgentFilters and ranks company + macro news, keeping full provenance (title, publisher, URL, published time)
FundamentalTechnicalAgentInterprets price, P/E, dividends, and precomputed indicators — never invents prices, never recalculates indicators
PersonalizedAdviceAgentSynthesizes findings with the user's strategy, goals, and risk appetite → three-bucket reasons + risks + items to watch
RiskEvidenceReviewerIndependent compliance gatekeeper — rejects unsupported claims, data older than 15 min, forbidden words ("การันตี" / guaranteed-return language); returns approve / revise / reject
How does the evidence contract work?

Every headline is cleaned and ranked first (strip URL garbage, dedupe across publishers, impact scoring), then inserted into the prompt with numbers [1] [2] … — the LLM may only cite those numbers. Citation badges on the detail card therefore come from the real digest, while summary cards strip citations for readability. Every reason line is auto-cleaned too: URLs, citations, and "no data available" placeholders are removed.

CHAPTER 06

UX engineering — designed to scan in 5 seconds

⏳ Instant ack + press debounce

Every button replies "processing…" immediately — no dead air — and locks for 30 s per user/action/symbol, so repeat presses get "already working on it" instead of duplicate AI calls.

📚 Progressive disclosure

Summary cards show 2-line telegraph headlines; the News button opens the full impact-ranked card with original-source buttons (URLs come only from the digest, never LLM-invented).

🏷 Three-bucket reasons — tagged on every line

Each reason line starts with its provenance tag so readers instantly know what backs it:

📰 [จากข่าว] · news 🏦 [จากงบ] · financials 📊 [จากสถิติ] · statistics

Applied consistently on the stock card, market brief, and daily digest (both Flex and plain-text fallback)

🚦 Traffic lights on every line

Advice and reason lines carry a badge so you can scan before reading:

🟢 Positive 🔴 Negative 🟡 Watch

Classified by a keyword classifier (Thai + English); anything ambiguous defaults to 🟡 Watch — no line is ever left untagged

🗞 News: fetch wide, then filter — and show the numbers

The news pipeline doesn't just take the first 8 headlines — it fetches wide, then selects:

  • Fetch (raw): up to 20 Finnhub company-news items (last 7 days, US symbols) or Google News RSS with 10 company + 10 macro headlines
  • Select: clean garbage/duplicates, score by market impact, keep the Top 8
  • Report: log [NewsPipeline] raw=M -> kept=N and the card shows “selected 8 from 23 fetched” (in Thai: "คัด 8 จากที่ดึงมา 23 ข่าว") so filtering is visible

The real lesson: the cost of an LLM system isn't just API fees — it's the downtime when pricing or models change. The failover chain is the cheapest insurance you can buy.

CHAPTER 09

Testing & shipping to production

Testing

  • 40 unit tests, fully offline: DATA_BACKEND=memory python -m unittest discover -s tests — no network, no API keys
  • Covers every card renderer, reason bucketing, tone classifier, idempotency, caching, and the workflow graph

Deployment

  • Git push → Cloud Run auto-deploy (asia-southeast1, service agent-stocks-service)
  • Secrets: the entire .env uploads as one secret named env_stocks, mounted as ENV_STOCKS — secret values override defaults in config.py
  • gunicorn: --timeout 240 --max-requests 200 to avoid stuck or overloaded workers
  • Diagnostics via /health and /debug/config (shows which env vars reached the container, never their values)
